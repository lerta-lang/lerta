# Objects

## Classes and structs

```
struct Point
  x: Int
  y: Int
  sum = @x + @y
  scaled = (k: Int) -> Point(x: @x * k, y: @y * k)

class Counter
  label: String
  count = 0
  increment = -> @count += 1

c := Counter(label: 'clicks')
c.increment()
print c.count
```

- `class` and `struct` declare a type at the top level. Its name cannot be the name of a top-level function or another top-level name: types and values share one namespace (`class A` then `A := 1` is an error, `'A' is already defined`). It may be that of a builtin, type or value, which it then shadows in the whole module (see [control flow](control-flow.md)). Like functions, types can be used anywhere in the module, so they can refer to each other and to themselves (`next: Node?`).
- **Members**, one per line:
  - `name: Type` is a field without an initializer: a constructor argument. If its type is optional, the argument may be left out, and the field is nil. A field may hold a function (`on_click: () -> void`); `b.on_click()` calls it (see [function values](functions.md#function-values)).
  - `name = value` or `name: Type = value` is a field computed at construction from its initializer.
  - `name = default value` or `name: Type = default value` is a constructor argument that may be left out; the field then has the value, computed as an initializer would be, in its place. `default` is not a [keyword](syntax.md#operators).
  - `weak name: Type?` is a field of a class that holds an object of a class without keeping it alive, so that two objects that refer to each other, as a parent and its children, are freed. Reading it gives the object, or nil once the object is freed; it can be assigned, and given to the constructor or computed as any field. Its type is written, an optional class, which cannot be a type parameter so far.
  - `weak! name: Type` is a weak field for an object that should outlive its holder: of a class type that is not optional, it is a constructor argument, which cannot be assigned afterwards, and reading it throws `weak object is gone` once the object is freed, including while the object's `deinit` runs.
  - `name = (params) -> body` is a method, which may be generic, as `apply = <T>(f: (Int) -> T): T -> f(@n)` (see [generic methods](#extend)). `init`, which takes no parameters and no type parameters, runs at the end of construction. In a class, `deinit`, which takes no parameters and gives no value, runs when the object is released (see below).
- **Generic classes and structs.** `class Stack<T>` or `struct Pair<A, B>` declares type parameters, which take no bound so far, and its type is written with as many type arguments, `Stack<Int>`. Each set of type arguments makes an instance, whose fields have the types they give and whose methods are generic methods with those type arguments (see [generic methods](#extend)); an instance is checked and compiled for its own, as a generic function is. Constructing one takes the type arguments written, `Stack<Int>()`, or else those that the expected type and the arguments give, as a generic function's are inferred (see [generic functions](functions.md#generic-functions)): `Pair(first: 1, second: 'a')` is a `Pair<Int, String>`. Instances of different type arguments are different types: a `Stack<Square>` is no `Stack<Shape>`. A member's written type may hold an instance of a generic class, struct or interface whose type argument holds a type parameter in a larger type, as `Node<T[]>` holds `T`, unless that instance's members lead back to the same type parameter, through the instances that they hold in turn, whose instances would then grow without end: `next: Node<Node<T>>?` in `Node<T>` is an error, and so are `b: B<A<T>>?` in `A<T>` and `a: A<B<T>>?` in `B<T>`, while `more: Pair<A, A[]>?` in `Pair<A, B>` is not, as the `B` of a `Pair` leads to no instance of it. Instances of the type parameters themselves, in any order, or of none of them, are not larger (`next: Node<T>?`, `swapped: Pair<B, A>`, `cache: Node<Int>?`). The interface that a class or struct satisfies counts as such a written type, whether its members use the type argument or not: `class A<T>: Source<A<T[]>>` is an error. The written types that the type arguments make in the fields must be valid, as those in a generic function's signature (see [generic functions](functions.md#generic-functions)): `Stack<Int?>`, whose `items: T[]` would be an `Int?[]`, is an error where it is first written or constructed. A type argument of an instance may nest types at most 32 deep, as a generic function's may: members that make instances of ever deeper type arguments, which a written type need not show, as `b = Map<String, A<T[]>>()` in `A<T>`, would never end, which is an error, `'A' needs instances without end, each with type arguments nested deeper`. A generic class or struct may have at most 1000 instances, as a generic function may: more is an error, `'A' needs more than 1000 instances`.
- **Construction** names its arguments: `Point(x: 1, y: 2)` (there is no positional form). A name alone is short for an argument of that name, as in an [anonymous struct](types.md#anonymous-structs): `Point(x, y: 2)` is `Point(x: x, y: 2)`; such arguments come before the others. A spread first, `Point(p..., x: 1)`, gives the arguments not written, read from `p`, which must be a value of the type constructed, not optional, and a name, `@` or a path of fields from one: the fields that are no arguments are computed again as for any construction, and of a class it constructs a new object, which shares what the fields hold. The arguments given are assigned first, then the initializers and the defaults of the arguments left out run in declaration order (each sees the arguments and the fields before it), then `init` runs. A field with an initializer is not an argument, so that what it computes cannot be overridden from outside, unless it is marked `default`. Where a struct is expected, `{ x: 1, y: 2 }` constructs it so too (see [anonymous structs](types.md#anonymous-structs)).
- **A construction that throws**, from an initializer, a default or `init`, releases the fields and frees the object without running its `deinit`; a weak reference to it then reads nil. An initializer cannot pass the object on, but `init` can, as by `registry.items.push @` or by throwing the object itself: if something else still holds the object when `init` throws, the program panics with `init threw an exception after its object escaped: <message>`, since that holder would be left with a freed object (see [panics](errors.md#panics)). A reference that the object's own fields hold, as a child's to its parent, does not count, since it goes with them.
- Inside methods, `@` is the object and `@x` its member `x` (`@.x` is an error). An initializer can only use `@` to read a field set before it (`@name`): the object is not complete yet, so it cannot be passed on or have its methods called.
- `p.x` reads a field and `p.m(...)` calls a method.
- **Mutability.** A class field can be assigned (`c.count = 1`) unless it is declared `const`. A struct field cannot be changed, and cannot be declared `var`.
- **Weak locals.** `weak name := value` and `weak var name = value` declare a local, in a function or in a block of the top-level code but not a top-level value, that holds an object of a class without keeping it alive. Its type is the class's optional type, `Button?`, which an annotation must write so; it reads as nil once the object is freed, so it is never narrowed: after `weak seen := button`, take the object with `if alive := seen`. A function literal that captures one captures it so, weak too; to capture `@` so, a [weak function literal](functions.md#function-literals) is shorter.
- Objects are reference counted, with no cycle collector. Assigning or passing an object shares it, and may retain it; whatever optimization can remove is removed. A struct can be part of a cycle only through something mutable it holds (an array, a map, a class object, or a function that captures a `var`), so immutable data is recommended.
- A struct is immutable, so copying it and sharing it cannot be told apart. The implementation may choose either (see [internals](../internals.md#structs-planned)).
- There are no static members (`static`), but for an [enum](types.md#enums)'s builtin `parse`. Functions related to a type are module functions; `extend` adds methods to a type, but not functions without a receiver.
- Why a function literal member is a method, one per type with `@` passed at call time, rather than a field holding a closure: closures capturing `@` would create a cycle in every object.
- **Equality.** Objects of a class compare by identity, unless the class has its own `equals` or `compare` (see below): `a == b` tells whether `a` and `b` are the same object, whatever their fields hold, and `!=` the opposite. The two sides may have different types, a class and a union or two unions, as long as both can hold objects of some class. Either side may be optional, compared as other [optional values](types.md#optional-values) are. Classes, and unions of classes, can also be [`Map`](types.md#map) keys, by identity.
- Structs compare by their contents: two are equal when they are of the same type and each field is equal as `==` compares it (a field of a class as the same object). Anonymous structs and arrays compare so too, and so do unions that hold them, whose values are equal when they are of the same member type and equal as it. A type whose part `==` does not compare, such as a function, cannot be compared. Such values can be `Map` keys, hashed by their contents; a key's arrays must not change while it is in a map, or it is no longer found. A value is equal to itself at once, but a value that holds itself through an array cannot be hashed, as a map key, nor compared with another such value: neither ends, and the program stops with a stack overflow.
- **Own equality and order.** A class or struct may declare its own `equals = (other: T): Bool`, which `==` and `!=` then call, wherever its values compare: as a whole, as a field of a struct, as an item of an array, as a map key. Or it may declare `compare = (other: T): Ordering`, whose result names a member of `Ordering` as `Ordering.LESS`, or as `LESS` where the written result type tells the enum, which gives `<`, `<=`, `>` and `>=` (`a < b` is `a.compare(b) == LESS`), and `==` too (`a == b` is `a.compare(b) == EQUAL`), so that the order and the equality cannot disagree; a type cannot have both (`T has both equals and compare, which gives its == too; leave out equals`). `T` is the type itself, and each must be of exactly its type (`equals of Point must be of type (Point) -> Bool, not (Int) -> Bool`), and its `Ordering` is that of std:builtins, which a module's own `Ordering` does not stand for. Such a type is a map key or a set item only if it also declares `hash = (): Int`, which must give equal values the same hash (`a set item must hash as it compares`); a `hash` without `equals` or `compare` is an error. They are methods of the type itself: no extend can declare `equals` or `hash`, which every type that `==` compares has already (`an extend cannot declare equals`), and an extend of a class or struct cannot declare `compare`. They cannot throw: an exception that leaves one makes a panic, `equals, compare or hash threw an exception`, since `==` and map keys could not pass it on. [Equatable, Comparable and Hashable](builtins.md#equatable-comparable-and-hashable) are the interfaces of these methods.
- **Operators.** An arithmetic or bitwise operator on a value of a type that it does not apply to otherwise calls the type's method of its name, which any type may declare, its own or through an extend, or a field of its name that holds a function, as an interface member is read: `a + b` calls `a.add(b)`, and `-`, `*`, `/`, `%`, `&`, `|`, `^`, `<<` and `>>` call `sub`, `mul`, `div`, `rem`, `bit_and`, `bit_or`, `bit_xor`, `shl` and `shr`, and prefix `-a` calls `a.neg()`. The right operand is the method's argument, of the type of its parameter, and the result is what the method gives, of any type (`Meters / Meters` may give a `Float`). Precedence is that of the operators, new operators cannot be declared, and `==`, `<` and the like come from `equals` and `compare` above. `a += b` assigns `a.add(b)`, and so on; since its target is then both read and assigned, it may only be a name, a field, an index or arithmetic (`xs[f()] += v` is an error). The method is found on the left operand, so `2 * v` does not call `v`'s `mul`. The builtin interfaces `Add` and the like name these methods for bounds (see [builtins](builtins.md#operators)).

## deinit

```
class File
  path: String
  deinit = -> print("closing #{@path}")
```

- A class's `deinit` runs when its object is released, when the last reference to it goes, before the references its fields hold are released. It cannot be called otherwise, and cannot throw (`deinit cannot throw`); an exception that a call in it throws makes a panic, `deinit threw an exception`, since no code that releases the object could take it. A struct has no `deinit`.
- Why a struct has no `deinit` and no `weak!` fields: if the time of its release were observable, the implementation could no longer choose between copying and sharing it. Breaking cycles is not needed for structs either.
- `deinit` is for cleanup: it may use `@` and call its methods, but must not keep a reference to the object, as in a field of another object; that stops the program with `deinit kept a reference to its object`.
- Objects still referenced when the program ends through `exit` or an uncaught `throw` are not released, so their `deinit` does not run.

## extend

```
extend String
  shout = (): String -> @ + '!'

extend Point
  total = (): Int -> @x + @y

extend<T> T[]
  second = (): T -> @[1]

print 'hi'.shout()
print [1, 2].second()
```

- `extend Type` at the top level, followed by an indented block of methods, written as a class's, gives a type more methods. Inside them, `@` is the receiver. An extend has no fields, and no `init` or `deinit`.
- Only `String`, the numbers, `Char`, `Bool`, `Binary`, arrays, maps, sets, `Iter`s, classes, structs and [interfaces](#interfaces) can be extended so far. Extending an optional, a function, a union, an anonymous struct or a tuple type is an error.
- **Extends of interfaces.** `extend<T> Source<T>`, or `extend Equatable`, gives its methods to every type that satisfies the interface, including the interface type itself; its type parameters are those of the interface's type arguments, which the type gives by its members (see [generic functions](functions.md#generic-functions)), and `Self` is the type, as in the interface. In the methods, `@` is of the type, and each method is checked and compiled for each type it is called on, as a generic method is. A method cannot have the name of a member of the interface, and does not count for satisfying an interface. A type that has a member of the name already, of its own or from an extend of a type, cannot call the method: the call is ambiguous, an error. Extends of two interfaces cannot give methods of the same name where both are in effect, since a type may satisfy both.
- Why extends rather than default implementations in the interface: the interface says only what a type must have, and a method of an extend cannot be overridden, so which code runs never depends on whether the type declares a member.
- **Generic extends.** `extend<T> Type` declares type parameters, as a generic function does, which the extended type must use: `extend<T> T[]` gives its methods to every array, `extend<V> Map<String, V>` to the maps whose keys are `String`s, and `extend<T> T[][]` to the arrays of arrays, while `extend Int[]` gives them to `Int[]` only. In the methods, the type parameters stand for the receiver's type arguments. A type parameter may have a bound, as a generic function's may, which the receiver's type arguments must satisfy where a method of the extend is used: with `extend<T: Comparable> T[]`, `[true].least()` is an error, `Bool does not satisfy Comparable`. Two extends of a type cannot give a method of the same name for different bounds. Two extends whose types overlap cannot give a method of the same name either, unless they are of one module and one of the types has no type parameters: that type takes the method of its own extend before the generic one, so `extend Int[]` and `extend<T> T[]` of one module may both give `head`, and `[5, 6].head()` calls the first, as the generic extend's other methods do; the same holds for `extend Promise[]` and `extend<T> Promise<T>[]`, since `Promise` is a `Promise<T>` without a value. A `Set<T>` is no `Map<K, V>`, so their extends do not overlap, and an extend of each may give a method of the same name. Of two modules, they are an error as before, since the generic extend's methods, checked in its module, would call another method than the module of the other extend does.
- **Generic methods.** The methods of a generic extend, and the methods of extends, classes and structs that declare type parameters of their own, as `map = <U>(f: (T) -> U): Iter<U> -> (f(x) for x in @)` does, are generic: the receiver gives the extend's type arguments, and the arguments give the method's own, which may have an interface bound, as those of a generic function are inferred (see [generic functions](functions.md#generic-functions)). Like a generic function, each is checked and compiled per instance, for each receiver type and set of type arguments; an error in its body names the instance, as in `(in String[].total)`. A generic method takes no named arguments so far.
- An extend is in effect in the module that declares it and in the modules that import that module directly, by any import, `import 'module'` included (see [modules](modules.md)), and, through modules that export from it and from one another, in each of those and in the modules that import one of them (see [exports](modules.md#exports)). It is not in effect further through imports: a module that imports one of those by an import does not get it.
- It is an error, at the extend's method, for the method to have the name of a member that the type has already, builtin or of its class or struct, or of a method that another extend in effect in the module gives the same type; extends of a generic type give the same type a method when some type matches both, as `Int[]` matches both `extend<T> T[]` and `extend Int[]`. When two imported modules' extends conflict, the error is at the second import. A generic extend may give a method the name of a builtin one that only some of the types it matches have, as `to_string` of `extend<T> T[]`: those types keep their builtin one.

## Interfaces

```
interface Shape
  area: () -> Int
  name: String

struct Square
  side: Int
  name = 'square'
  area = -> @side * @side

describe := <T: Shape>(shape: T) -> print("#{shape.name}: #{shape.area()}")

describe Square(side: 3)
describe { name: 'dot', area: -> 0 }

shapes: Shape[] = [Square(side: 2), { name: 'dot', area: -> 0 }]
print shape.area() for shape in shapes
```

- `interface Name` at the top level, followed by an indented block of members, `name: Type`, one per line, declares what a type must have to satisfy it. It has at least one member; only std:json's [Jsonable](std.md#stdjson) has none. Its name is in the namespace of types and values, and may be that of a builtin, as a class's.
- **Generic interfaces.** `interface Source<T>` declares type parameters, which take no bound, and its type is written with as many type arguments, `Source<Int>`. A type satisfies it with the type arguments in the members' types. The types that the type arguments make in the members must be valid, as the fields of a [generic class](#classes-and-structs): `Source<Int?>`, whose `items: () -> T[]` would give an `Int?[]`, is an error where it is first written. A member's type may not hold larger instances that lead back to it, as those of a class may not.
- **`Self`** in the members stands for the type that satisfies the interface: `equals: (Self) -> Bool` is satisfied by a `Point` with `equals: (Point) -> Bool`. An interface whose members name `Self` can only bound type parameters, not be a type of values, since its values could not tell which type `Self` is.
- A type **satisfies** an interface when it has, for each member, a method, a field or a property of the member's name and of exactly its type. Nothing needs to declare that it does (structural typing). A method may come from an extend in effect where it is checked; one with type parameters of its own has no one type, and satisfies no member. A function member, such as `area: () -> Int`, is satisfied alike by a method and by a field that holds a function. A union satisfies a member by a method that every member of it has, or by a field that every member has, of the member's type, as it is called or read through the union (see [unions](types.md#unions)); a method in some members and a field in the others do not.
- **Declaring an interface.** `struct IndexError: Error` or `class Counter: Source<Int>` names an interface that the class or struct satisfies, which is checked where it is declared. Each member of the interface that the type's own members do not declare becomes a field of the member's type, a constructor argument, before the type's own fields; so `struct IndexError: Error` alone, without a body, declares a struct with a `message: String`. Such a field follows the rules of the type's others: it can be assigned in a class, not in a struct. A method of an extend of the type cannot stand for such a member, which is a field already. The interface may name `Self`, as a bound may. The type still satisfies other interfaces by its members alone, and only one interface can be named so far.
- An interface bounds type parameters (see [generic functions](functions.md#generic-functions)), and is also a type of values: an **interface value** holds a value of a type that satisfies it, through which `shape.area()` and `shape.name` read the members. A value converts to an interface type, or to one optional, where one is expected, as a value converts to an optional type, provided that its type satisfies the interface where it is converted; the extends in effect there give the members. An interface type satisfies itself, so an interface value can be given to a type parameter that the interface bounds.
- So far only references convert to interface values, not `Int`, `Float`, `Bool`, `Byte` or enum values, nor does an interface value to another interface. A union converts, whatever its members, as it satisfies the interface by what every member has (see [unions](types.md#unions)); a union of `Int` and `String` is a `Stringable`. Interface values cannot be compared with `==`, nor be map keys, and C functions cannot take or return them.
- Members are read-only: an interface has no member that must be assignable, so its members are written without `const` or `var`, and have no value, and an interface value's members cannot be assigned. A function member is called, as a method is, not read as a value.
- Why read-only: a struct's field, a `const` field and a method cannot be assigned, so an assignable member would leave them out, and an assignment whose meaning depended on how the member is satisfied would be a setter.
- Why exactly the member's type, not one assignable to it: the generic code is checked with the type the member has (see [generic functions](functions.md#generic-functions)), so a `String` field for a member `name: String?` would fail in that code rather than where the type is given.
