# Style

These conventions also cover features not implemented yet. The compiler does not check them; [`lerta fmt`](compiler.md#fmt) checks and fixes them, except those that [the roadmap](../roadmap/programs.md#tools) lists as not applied yet.

- **Naming**: variables, functions, methods, fields and module names are `snake_case`. Types, classes and interfaces are `PascalCase`. A `const` whose value is a literal (such as `MAX_SIZE := 100`) and an enum member are `SCREAMING_CASE`. A `const` holding a computed result is an ordinary variable and is `snake_case`. This matches C names imported through FFI naturally.
- **String literals**: use `'...'` whenever it can be written with `'...'`. A `"""` literal stays as it is written, though `'''` could write it. The lines of a `"""` or `'''` literal after its first are one level deeper than the line that it starts on, keeping their indentation relative to each other, and a blank one is empty.
- **Inside `{}`**: put spaces in an anonymous struct, a map and their types (`{ x: 0, y: 1 }`), but not in an interpolation (`#{x}`).
- **Spacing**: one space on each side of a binary operator (those of [operators](syntax.md#operators) but `...`, the words among them included), of `=` and the compound assignments (`+=`), and of `->` (but after an opening bracket or at the start of a line, `(-> x)`), and after a comma, after every `:` and after `not`; none around the `...` of a range or a spread (`0...n`, `xs...`), inside `()` and `[]`, inside the `<>` of type parameters and arguments or before one that follows a name or `extend` (`Map<K, V>`, `extend<K, V> Map<K, V>`, though the syntax allows a space there) or before the `[]` of an array type (`Int[]`), around a `.` or a `?.` inside a line, before a postfix `!`, before the `?` of an optional type, before a comma or a `:`, between a callee and its `(` (a call without parentheses keeps one after its callee: `f (a), b`), or after a unary `-` or `@` (`@x`).
- **Comments**: their text is kept as it is written. One that ends a line follows two spaces; one on a line of its own is indented as the line of code after it, or as the one before it where its column in the source is greater than that of the line after it, as at the end of a block, or where no line follows it.
- **Multi-line literals**: where it can be written without brackets, write it without brackets, the names of an import included. Where only a member call after the closing bracket keeps them, put it on the line after the block (`.join('')`). A function returning one ends with `return` and the block, since a body is not a literal.
- **Layout**: indent by two spaces for each level. The lines inside brackets are one level deeper than the line that opens them, and the closing bracket goes back to that line's level, at the start of a line. The closing brackets of brackets opened on one line share a line (`])`), and what follows a closing bracket stays on its line, but a member, which goes on a line of its own (see **Multi-line literals**). No line ends with whitespace. Lines end with LF, and a file ends with one.
- **Line length**: up to 100 columns per line.
- **Blank lines**: at most one in a row.
- **Long lists**: a list that does not fit on one line (parameters, arguments, the items of an array or a map, the names of an import, the patterns of a `when`) goes on lines of its own inside the brackets, or in a bracketless block (for patterns, the [block of `when`](control-flow.md#case-with-a-subject), with `then` on the line after it; for the arguments of a call that is a statement or a whole value on a line of its own, [a block below the callee](syntax.md#bracketless-blocks) if the callee is one of a [call without parentheses](syntax.md#calls) and the call has no type arguments), each holding as many items as fit when every item is simple: a name, a short literal, a parameter `name: Type`, `name: value` with such a value, or a pattern. Otherwise each item, as a call or an operation, or one that stands for a line of text, goes on a line of its own (see [lines inside brackets](syntax.md#lines-inside-brackets)). A line holding several items ends with a comma, except the last line of the list; a line holding one item does not, so that a comma and a line end do not look like two kinds of separator. A function whose body takes lines of its own inside brackets ends the list on the line where the brackets open if it is the last item, with the closing bracket on a line of its own (`xs.map((x) ->`, the body, `)`); otherwise each item goes on a line of its own.
- **Modules**: a library module contains only code that builds the exported values. Put code to run in a separate entry file.
- **Calls without parentheses**: call a function or a method without parentheses at the start of a statement on a line of its own, the last expression of a block included (`write_group writer, item, indent`, `xs.push x`), wherever the language allows it (see [calls](syntax.md#calls)). On the line of an arm or of a function literal, keep the parentheses (`when Call then generate_call(g, expression)`, `-> Group(fields)`).
- **Implicit return**: end a function with its value (`x`), not `return x`, except a multi-line literal (see **Multi-line literals**); do not end a function returning nothing with a bare `return`.
- **Shorthand**: when the value of a named argument or a field is a variable of the same name, write the name alone: `Point(x, y: 2)`, `{ a }`. `lerta fmt` applies it only to the fields of an anonymous struct so far; to named arguments, as `Point(x: x)`, it is [planned](../roadmap/programs.md#tools).
- **Parentheses**: do not write parentheses that change nothing, except where another rule asks for them (**Ranges**), to clarify `and` mixed with `or` and around a `then`/`else` inside the `then` value of another (`a then (b then x else y) else z`), whose `else`s are hard to pair otherwise.
- **Cast fallbacks**: write `x as T ? y`, not `(x as T?) ? y`.
- **Nil initial values**: write `var found: String?`, not `var found: String? = nil`.
- **Empty initial values**: write `names: String[]`, not `names: String[] = []`, and `seen: Set<String>`, not `seen := Set<String>()` or `seen: Set<String> = Set()`; the same for `Map`. A `var` and a field keep their values.
- **Negated is tests**: write `x is not T`, not `not (x is T)`.
- **Postfix forms**: if the body of `while`/`for`, or of an `if` without `else` whose value is not used and which is not the whole body of an `else`, is one statement other than a declaration, without a postfix form of its own, use the postfix form (`return nil if not found`). If it exceeds 100 columns or takes more than one line, use the block form even for one statement. Do not stack postfix forms (`x += 1 for x in xs while ok`). A `for` whose body is one statement with a postfix `if` is written as a block holding it (`for x in xs`, then `total += x if x > 0`), not as `total += x for x in xs when x > 0`, which the formatter cannot tell from it.
- **Branches**: branch two ways with `if`/`else`, including for a value and on a subject (`if x is T`, `if kind == 'a'`), and three or more ways with `case`. A two-way `case` without `else` that handles every type or member of its subject (see [case with a subject](control-flow.md#case-with-a-subject)) stays a `case`: a type or member added later then fails to compile, where an `if` would take it to `else`. A two-way value that fits on one line is `c then a else b`. Without `else`, `then` gives nil, so leave out `else nil`: `name then greet(name)`. An arm whose body is one statement that its line can hold (see [case without a subject](control-flow.md#case-without-a-subject)) and that fits on it is written on it, `when 1 then 'one'` or `else pass`, and otherwise as a block; a block of the name `pass` alone stays one, as on the line it would be the arm that does nothing. An `else` whose body is one `if` is `else if`, unless a comment comes before the `if`. An `if`, a `case` or a `try` whose blocks are on the lines below starts a line of its own, one level deeper than the line that takes its value (`x :=`, then `case n` on the next line), where the grammar allows it (see [bracketless blocks](syntax.md#bracketless-blocks)).
- **Type bodies**: write type-only fields (constructor arguments) first, then those with a `default`. Do not write `const`/`var` when it equals the default.
- **Constructor arguments**: write the members of a class or struct in parentheses on its line (`struct Point(x: Int, y = default 0)`) when all are constructor arguments and they fit, and otherwise in a block.
- **Function bodies**: a body of one statement that fits on the line of the `->` goes on it (`(x) -> x + 1`), and otherwise in a block below it, as does one statement that a line cannot hold: a declaration, or one that holds a block, as a `case`, a `try` or a loop without a postfix form.
- **Functions without parameters**: write `-> body`, not `() -> body`, unless it has a return type or type parameters (`(): T -> body`, `<T>() -> body`).
- **Type annotations**: omit a type that can be inferred: the return type of a function, the type of a parameter of a function literal whose type is expected (`xs.map((x) -> x * 2)`) or that has a default, and the type of a variable or of a field with a value. The type of a `var` whose value is `Map()` or `Set()` goes to its type arguments: `var seen = Set<String>()`. Write it where the language requires it (recursion, `nil` alone, an empty array) or where it changes the type (`var x: Int? = 1`), and in generic functions, classes, structs and extends, whose code is checked only per instance.
- **Enum members**: where an enum is expected, write its member alone (`kind == INTEGER`, not `kind == TokenKind.INTEGER`; see [enums](types.md#enums)), unless a name in scope takes the member's name. Do not import an enum only to name its members.
- **Function types returned**: name a function type that a function literal returns with a `type` alias, `type Combine = (Int, Int) -> Int`, rather than writing it in parentheses before the `->` of the body, where the arrows run together.
- **Top-level order**: declare a top-level value above the code that uses it, wherever the order allows.
- **Unused names**: name an unused variable `_`.
- **Ranges**: parenthesize an end that is an operation (`0...(n - 1)`) for readability; `...` binds weaker than arithmetic, so the parentheses do not change the meaning.
- **Integer types**: quantities (counters, sizes, indexes, `length`) are `Int`, which every API takes. Unsigned types are for bit operations, FFI and `Byte`.
